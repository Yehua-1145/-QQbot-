# 接入微信：可行性评估

> 结论先说：**能做，但只有两条路值得走** —— 企业微信单向推送（合规、简单）
> 和 无障碍 UI 自动化（本地、实验性、有封号风险）。
> 逆向协议/hook 那条路**不建议**，理由和 NapCat 生态的教训是同一个。

## 微信的四条技术路线

| 路线 | 原理 | 能收消息 | 需要公网 | 合规性 | 维护成本 |
|---|---|---|---|---|---|
| **① 企业微信群机器人 Webhook** | 官方接口，POST 一条 JSON 到 `qyapi.weixin.qq.com` | ❌ 只能发 | 不需要（只出网） | ✅ 官方支持 | 极低 |
| **② 企业微信自建应用** | 官方接口 + 回调 URL | ✅ | ✅ 需要 | ✅ 官方支持 | 中 |
| **③ 无障碍 UI 自动化** | 我们用系统无障碍点微信界面 | ✅（读通知/读屏） | 不需要 | ⚠️ 灰区，可能被判自动化 | 高（UI 一变就崩） |
| **④ 逆向协议 / hook** | 注入 PC 微信或模拟协议 | ✅ | 不需要 | ❌ 违反用户协议 | 极高（版本一更就废） |

## 为什么不做 ④

```
· 微信版本更新频繁，hook 每次都要重新逆向 → 三天两头坏
· 违反《微信个人账号使用规范》，封号是常态
· 灰产属性重，个人号协议基本是收费黑盒，法律风险高
· 这正是 SnowLuma 那类项目的处境：上游一关，所有人陪葬
```

我们自己的定位是「不用电脑、不用 root、全程本机」——
如果为了微信去绑一个随时会坏的注入层，等于把刚拆掉的雷又埋回去。

## 路线 ①：企业微信 Webhook（建议先做这个）

**优点**：官方接口、免费、5 分钟接好、不需要公网、不会封号。

```bash
# 群机器人地址（在企业微信群设置里拿）
https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxxxxxx

# 发一条 markdown
curl -s -X POST "$WEBHOOK" -H 'Content-Type: application/json' \
  -d '{"msgtype":"markdown","markdown":{"content":"**电量** 78%\n**位置** 家里"}}'
```

**能做什么**：

```
· 机器人主动推消息（日报、告警、任务完成通知）
· 定时任务跑完把结果发到群里
· 手机状态（电量/网络/前台 App）定时播报
```

**不能做什么**：

```
· 收不到群里的消息 → 做不了"对话式机器人"
· 不能 @ 触发 → 交互必须是 App 内部的
```

**工作量**：半天（加一个 `wecom_webhook` 配置项 + 一个 `notify_wecom()` 工具，agent 里多一个 tool）。

## 路线 ②：企业微信自建应用（要公网，先放）

能双向，但要：

```
· 企业微信后台建应用、拿 corp_id / secret / agent_id
· 配一个公网可达的回调 URL（要 80/443 + 校验签名）
· 我们「全本地」的定位就破了 —— 得给手机做内网穿透
```

除非以后做「云+端」双模式，否则不建议。

## 路线 ③：无障碍 UI 自动化（实验性，可选）

**思路**：微信没有开放接口，但**我们能操作屏幕**。

```
1. 监听通知栏的微信消息（我们已有 a11y 的 /notify 接口）
2. 拿到「谁说了什么」
3. 需要回复时：打开微信 → 找到那个会话 → 输入 → 发送
```

**工作量**：2~4 天出 demo（会话定位、输入框聚焦、发送确认），长期维护成本高。

**风险要说清楚**：

```
· 微信有反自动化检测，长期高频操作可能限流或封号
· 界面一改就失效（微信更新频繁）
· 锁屏/后台时不可用（必须先点亮屏幕）
· 群聊里很难稳定"只在被 @ 时回复"
```

如果要做，建议：

```
· 做成「实验功能」，默认关闭，README 明确写风险
· 只做私聊/小号，不建议挂主号
· 频率限制（比如每分钟最多回 1 条）
```

## 建议的落地顺序

```
第一步（0.5 天）  企业微信 Webhook 单向推送
                  → 立刻可用、零风险、覆盖"通知/日报/告警"场景

第二步（看需求）  无障碍微信收发（实验）
                  → 只在你愿意用小号试的时候做，默认关闭

不做              hook / 协议逆向；企业微信自建应用（要公网）
```

## 和现有代码的关系

若做路线 ①，几乎不用改架构：

```
aibot/config.py     加 WECOM_WEBHOOK = _env("WECOM_WEBHOOK", "")
aibot/agent.py      加一个 tool: notify_wecom(text)
aibot/webui.py      设置页 /api/settings 加 wecom_webhook 字段
console.html        设置页加一张「通知渠道」卡片
```

若做路线 ③，则会新增一个 `aibot/wechat_ui.py`，复用 `A11yServer` 的
`/dump`、`/tap`、`/notify`、`/type` 四个接口，不碰协议层。

## 一句话

**微信值得接，但只接官方的那一半。** 单向下发消息是稳赚不赔的；
想双向对话，就用我们自己的控制台，或者接受无障碍方案的实验性和风险。
